Stock-file patches
==================

The PlayerBots system lives entirely in Projects/UOContent/CustomBots, with
one exception: six stock ModernUO files need a small patch, because they
ARE engine files and cannot live in CustomBots/.

Both installers apply these for you now. They ship as unified diffs in
patches/ and go on with git apply, in the "Patch the engine" step right
after the ModernUO clone. The step is idempotent (a patch already applied is
detected and skipped) and never fatal: if upstream has moved on and a patch
no longer applies, the install warns and carries on, and you can apply it by
hand from the descriptions below.

If you are deploying the bots onto a ModernUO clone by hand, without the
installer, apply them yourself.

Stock-file patch required by the housing system (2026-07-05)
------------------------------------------------------------
CustomBots/BotHousing.cs places ownerless, ageless scenery houses
(RestrictDecay = true). Stock ModernUO deletes any owner-less house
10 seconds after world load, which silently reaped the whole land
rush on every boot. One-line patch in:

  Projects/UOContent/Multis/Houses/BaseHouse.cs  (~line 3255)

  - if (m_Owner == null && Friends.Count == 0 && CoOwners.Count == 0)
  + if (m_Owner == null && Friends.Count == 0 && CoOwners.Count == 0 &&
  +     !RestrictDecay)
    {
        Timer.StartTimer(TimeSpan.FromSeconds(10.0), Delete);
    }

If deploying playerbots onto a fresh ModernUO clone, re-apply this or
bot houses will vanish on the first restart.

Stock-file patch: let a bot be one side of a trade window (2026-08-26)
----------------------------------------------------------------------
CustomBots/BotTradeWindow.cs lets a player buy from a bank hawker the way
players always bought from each other: drag gold onto them and the real
secure trade window opens, with the bot holding up its half.

Stock ModernUO assumes both sides of a trade are connected clients and
dereferences NetState without checking. A PlayerBot is a real PlayerMobile
with no connection, so the trade constructor threw on the first send.
Patch in:

  Projects/Server/SecureTrade.cs

  Every from.NetState.X / to.NetState.X becomes from.NetState?.X — in the
  constructor, in Close(), and in both Update() branches. A participant
  with no client simply receives no packets, which is correct: there is
  no window to draw. Containers, accept flags and item transfer are
  untouched, so a player-to-player trade behaves exactly as before.

Nothing else was needed. Mobile.OpenTrade is virtual, so PlayerBot
overrides it rather than being patched, and the trade is registered on
the player's own NetState.Trades list.

If deploying playerbots onto a fresh ModernUO clone, re-apply this or
dragging gold onto a hawker does nothing at all.

Stock-file patch: public moongates for young players (2026-08-23)
-----------------------------------------------------------------
This shard runs the T2A ruleset with Felucca as the ONLY enabled map
(Configuration/expansion.json -> MapSelectionFlags). Stock ModernUO
hands young players a reduced moongate destination list that omits
Felucca on purpose, assuming Trammel exists to send them to instead
(PMList.T2AListsYoung = { Trammel }). With Trammel disabled that list
filters down to nothing, MoongateGump.DisplayTo returns before sending
anything, and a young player walking into a public moongate gets the
gate sound and no gump at all -- the gates look broken.

Staff characters never hit it: their access level is inherited from the
account at character creation, so they are never flagged young. Every
character made on a normal (non-staff) account is, which is why this
only showed up for regular players. Patch in:

  Projects/UOContent/Items/Misc/PublicMoongate.cs
  (MoongateGump.DisplayTo)

  The expansion switch now yields both the full and the young list.
  If filtering the young list by the enabled maps leaves nothing, it
  re-filters using the full list, so the gate always opens something.

The young player system itself is now OFF as well (2026-08-23). It is a
UO:R-era feature that did not exist in T2A, and switching it off removes
the cause of the above outright, along with the "(Young)" name suffix,
young monster protection, the Haven transport option in the help gump,
the New Player Ticket, and the young death teleport. It is a feature
flag, not a code change:

  Distribution/Configuration/FeatureFlags/flags.json

  [ { "Key": "young_player_system", "Enabled": false, ... } ]

Both installers write that file next to expansion.json, so a fresh
install gets it too (install.ps1 / install.sh, right after the T2A
expansion config). Startup confirms it with:

  Feature Flag system initialized with 1 flags, ...

The moongate patch above is kept regardless -- it is the safety net for
any ruleset that filters a player's facet list down to nothing.

Stock-file patch: mounts only tire under load (2026-08-29)
-----------------------------------------------------------
Stock ModernUO charges a mount one step of fatigue for every step the
rider runs, laden or not. At 3840 steps that is roughly an hour of
riding before "Your mount is too fatigued to move" -- on a horse that is
carrying nothing. Upstream turns that off with a setting, but only from
Stratics Age on (stamina.useMountStaminaOnlyWhenOverloaded defaults to
Core.SA), so a T2A shard gets the old behaviour. Patch in:

  Projects/UOContent/Misc/StaminaSystem.cs

  1. The setting now defaults to true instead of Core.SA. A horse tires
     from the load it hauls, not from being ridden. Put
     "stamina.useMountStaminaOnlyWhenOverloaded": "false" in
     Configuration/modernuo.json for stock behaviour.

  2. Fatigue now counts the pack train as load, not just the rider.
     GetPackTrainOverweight() adds the mount's own pack (a beetle) plus
     every pack beast out with the rider, and EventSink_Movement folds
     that into the overweight figure passed to ProcessMountMovement.

     A beast is over its capacity at 40 + 3.5 * Str stones, the same
     formula players use -- BaseCreature inherits Mobile.MaxWeight,
     which is int.MaxValue, so nothing in stock ever reports a laden
     pack animal as heavy. A pack horse (Str 44-120) hauls 194-460
     stones free; past that the mount starts tiring. Only beasts with a
     StrongBackpack count, which is the engine's own test for a pack
     animal (BaseCreature.DisplayWeight).

The unmounted case is untouched: a player on foot still loses stamina
for their own weight only, and an overloaded pack horse does not tire
someone walking beside it.

If deploying playerbots onto a fresh ModernUO clone, re-apply this or
horses go lame on long rides for no reason.

Stock-file patch: T2A travel rules in Felucca dungeons (2026-08-30)
-------------------------------------------------------------------
You could not mark a rune inside a Felucca dungeon, and the message you
got back was "Thy spell doth not appear to work..." -- which reads like a
fizzle, not a rules block. Nor could you recall or gate in or out of one.

That is stock ModernUO, and it is not a bug there: it is the later-era
Felucca ruleset, where magical travel in dungeons was shut off. It is
wrong for a T2A shard. In 1998-99 dungeon runes were ordinary kit and
recalling out of Deceit with a full pack was normal play. Patch in:

  Projects/UOContent/Spells/Base/SpellHelper.cs

  The Dungeons(Fel) column of the m_Rules travel table is now true for
  Recall From, Recall To, Gate From, Gate To and Mark In. Nothing else in
  the table changes.

What stays blocked, on purpose:

  - The Lost Lands (the T2A(Fel) column, x 5120-6144 / y 2304-4096). No
    recall, gate or mark there. That restriction is period-correct -- the
    Lost Lands were meant to be reached through the passages, not by rune.

  - Wind, both facets. Also period-correct.

  - Khaldun. It sits in the dungeon map block and reads as a Felucca
    dungeon, but it has its own column in the table and stays false. It is
    not T2A content.

The table is a hardcoded bool[,] with a "TODO: Move to configuration" on
it upstream, so there is no setting to flip -- it has to be a patch.

If deploying playerbots onto a fresh ModernUO clone, re-apply this or
dungeon runes cannot be made.

Stock-file patch: let bots path through doors (2026-09-01)
-----------------------------------------------------------
The pathfinder decided whether a closed door was passable by asking the
mobile whether it was a door-opening creature:

  Projects/UOContent/Engines/Pathing/BitmapAStarAlgorithm.cs  (~line 143)

    if (m is BaseCreature creature)
        _currentMobileIgnoreDoors = creature.CanOpenDoors;
    else
        _currentMobileIgnoreDoors = false;      <-- every PlayerBot

A PlayerBot is a PlayerMobile, not a BaseCreature, so it landed in the
else and every closed door was a solid wall to it. PlayerBot.Move has
always opened a door it walks into, the way the client's auto-open does,
so the pathfinder and the mover disagreed: A* reported "no route" for a
room the bot could have walked straight into. PathFollower answers a
failed path by stepping at the goal anyway, so the bot walked into the
wall beside the door and shuffled there until the combat code gave up on
the monster. Every monster in the game could path through that same door.
Only the bots could not.

The patch sets the flag for PlayerBots, and adds a second flag so a bot
only routes through doors it could actually open:

    _currentMobileUnlockedDoorsOnly = m is Server.CustomBots.PlayerBot;

    // in the per-cell item test
    && !(_currentMobileUnlockedDoorsOnly
         && item is Server.Items.BaseDoor { Locked: true })

The creature rule is deliberately untouched. CanOpenDoors has always meant
locked doors as well, and changing it would change monster behaviour.

The locked test costs nothing on the hot path: it is only reached for a
mobile that ignores doors at all, standing on a cell that holds one.

Measured before and after on a live shard: door work (bots routing to or
opening a door to reach a foe) went up about sixfold, and engagements rose
roughly 30%. Two things that sound related but are NOT the cause were
tested and ruled out -- raising pathfinding.maxSearchNodes from 1000 to
4000 recovered zero extra routes (every budget failure was genuinely
unreachable), and widening the 38-tile search window to 64 moved the path
failure rate only 16.3% -> 14.7%, which is not worth the cost. Both were
reverted.

If deploying playerbots onto a fresh ModernUO clone, re-apply this or bots
cannot path into any room whose door is shut.
